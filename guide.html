Download, load, evaluate

The data is hosted on Hugging Face in the repository ChangChrisLiu/E3D-Desktop-Disassembly. The repository still carries the dataset's earlier name, E3D-Desktop-Disassembly; it holds the same data as EoL3D.

Open on Hugging Face

  1. Download

    Fetch the whole repository, or only the folders one task needs.

    The hf command comes with the huggingface_hub Python package. The repository is public: no account or token is needed to read it. The commands are for a Unix shell; $DATA is the folder the data goes to.

    With huggingface_hub older than 1.0, use huggingface-cli download in place of hf download, with one --include followed by all the patterns.

    Which folder holds what

  2. Load

    Read one desktop of the scanner annotations, and the question-answer records.

    Scanner annotations

    One folder per desktop, annotations/scanner/D<nn>/. Step S01 is the untouched machine; every other image is taken after that step's operation.

    images/S<nn>.png
    The scanner image of step nn, 1600 × 1600 pixels.
    labels/S<nn>.png
    The label map: the instance id of each pixel (0 is background). Take a part's pixels from here; where two masks overlap, it gives each pixel to one part.
    annotations.json
    COCO: one annotation per part and step, with class, box, the visible and the complete (amodal) mask as RLE, visibility and occlusion. A part in place but fully covered has iscrowd 1 and an empty visible mask.
    instances.json
    Each part: key, class, relations, its state at every step and the step it leaves.
    sequence.json, frames.json
    Step names and operations, each part's state timeline, the source file of each image.

    Question-answer records

    JSON lines, one question per line: one file per camera (scan, oak1, oak2) and one for the questions about operations and plans (multi). prompt is what a model is shown; label holds the answer, how it is checked and the desktop's train / test split. Images are referenced by id; the .images_manifest.jsonl beside each file gives their paths. Standard library only.

    To put the questions to a model, convert them with vlm_to_chat.py (step 3): it draws the outlined parts on the images and adds each task's answer format.

  3. Evaluate

    Score a file of predictions with the kit of a benchmark track. The kits are also in the code repository.

    Detection and instance segmentation What is measured

    Scoring needs numpy and pycocotools; the baselines need the pinned versions in requirements.txt (install torch and torchvision for your CUDA first, as the kit's README says). The self-check scores the ground truth against itself and must give a perfect score.

    Predictions are a COCO results list: image_id, category_id (the pack's ids), score, bbox [x, y, w, h] and / or segmentation as COCO RLE, on the full 1600 × 1600 frame. For complete (amodal) masks, build the files with --masks amodal into another folder. eval_coco.py writes metrics.md and metrics.json.

    Question answering What is measured

    The tools need Python 3.11 or later and PyYAML (Pillow for crops and marks). The self-check sends every gold answer through the scorer and must give a perfect score on every task.

    Do the same for scan, oak1 and oak2, and score each file separately. vlm_score.py writes <name>.score.md and .score.json: every task with strict and lenient parsing, intervals from a bootstrap over desktops, and reference lines beside each task.

    Depth from a single image What is measured

    The two scripts need numpy alone. The reference is made from the scanner's point clouds; a model sees annotations/scanner/D<NN>/images/S01.png and writes its depth for that picture in metres.

    The scorer prints the errors as predicted, the median scale, and the errors after dividing each prediction by its scale; --json also writes them per image. Other desktops and steps work the same way (--desktops, --step).

The dataset, file by file

EoL3D is built from 66 real desktop computers, used and retired from service. An operator takes each one apart step by step; after every step the remaining assembly is recorded from four fixed views, and an operation log names the part and the action of the step. Below: what each part of the release holds, where it lives in the repository and how to read it.

One step, four views, the log

Step 1 is the machine before any action. After every later step, the 3D scanner looking straight down and three cameras record what is left: two OAK cameras, one nearly overhead and one at an angle, and a RealSense camera at an angle. The operation log gives each step its name and its actions: verb, part and tool.

Scanner
raw/scanner/<batch>/<batch>/<NN>/RGB<n>1/: a burst of colour images per step, P_0.png, P_1.png, …
OAK
raw/oak/Desktop NN/Disassemble/Camera_1|2/<step>/: colour JPEG, colour aligned to depth (PNG), raw depth (.npy, .png), point cloud (.ply)
RealSense
raw/realsense/Desktop NN/Disassemble/<step>/: colour, raw depth (.npy), point cloud (.ply)
Calibration
Calibration/ in each desktop folder of the cameras
Log
annotations/scanner/D<nn>/sequence.json: per step its name, type and actions; verbs: unscrew, disconnect, open, release, remove, displace, reorient
{"step": 10, "name": "Open Power Module",
 "actions": [{"verb": "displace", "target": "psu.01", "tool": "none"}]}

Read it right Every picture of a step is taken after that step's action: on S05 the part removed at step 5 is already gone. Of each scanner burst, frames.json names the image the masks were drawn on.

Instance masks

Every scanner frame carries an instance mask for every part it shows, in 24 classes, and every frame was confirmed by a human annotator: 2,800 frames, 3,217 parts, 84,225 annotations.

Folder
annotations/scanner/D<nn>/, one per desktop
Pictures
images/S<nn>.png: the scanner picture of step <nn>, the raw file byte for byte
Label maps
labels/S<nn>.png: 16-bit instance ids, 0 = background
COCO
annotations.json: segmentation (visible mask, RLE), amodal_segmentation, amodal_bbox, visibility, occlusion_ratio, occluders, clean, iscrowd, attributes (instance key, state, placement)
Per desktop
frames.json (per step), instances.json (per part), sequence.json (steps and state timeline)

Read it right Take pixels from the label map, not from segmentation: where two confirmed masks overlap, the map gives each pixel to one part. instance_id holds within one desktop; join on key.

Visible region and complete extent

Parts cover each other. Each annotation holds two masks: the region the scanner sees, and the complete extent of the part, including what other parts cover. It also says how much is hidden and by which parts.

Visible
segmentation, bbox, area
Complete extent
amodal_segmentation, amodal_bbox, amodal_area
Hidden
occlusion_ratio (share of the complete extent hidden), occluders ([{"id", "px"}], the parts that hide it)
Label
visibility: visible, visible_tiny, too_small, occluded_partial, occluded_full; clean: not covered at all

Read it right A part labelled visible can still be partly covered; clean is the test for “not covered”. A crowd row (iscrowd: 1) is a part in place but fully covered: empty visible mask, complete extent kept.

Part states

Every part has a state and a placement at every step, so a part can be followed through the whole teardown, up to the step it leaves the case.

Per step
instances.json: states["<step>"] = state and placement; leaving: the step the part leaves, and the frames before and after
Timeline
sequence.json: timeline, runs of (from, to, state, placement) per part
States
closed, displaced, fastened, installed, loosened, open, plugged, present, removed, unplugged
Placements
in_chassis, on_bench

Relations and removal order

Relations between parts (connected, fastened, covered, locked, blocked) say what has to come off before a part is free. With the states, they give the removal order. Before the CPU of this desktop could come out:

  1. 1Cover covers the CPU fan
  2. 2–5Cooler screws fasten the fan
  3. 6Fan connector is unplugged
  4. 7CPU fan covers the socket lever
  5. 8Socket lever locks the CPU
  6. GoalCPU is free to come out
Per part
instances.json: parent, attached, mounted_on, fastens, socket_host, captive, attrs.cable_owner
Graph
vlm/vlmpack_2026-11-05/data/vlm_<unit>.oracle.jsonl, the lines of "type": "desktop": edges, groups, instances, log
Edge types
connected_to, fastened_by, covered_by, locked_by, blocked_by

Read it right An edge reads from the part that waits: {"target": "cpu.01", "type": "locked_by", "blocker": "cpu_socket_lever.01"} means the lever is dealt with before the CPU.

Component pictures

After the teardown, the removed parts were laid out on the bench and photographed, and each part was masked on its own, so a part can be recognised outside the machine too: 64 shots, 626 annotations.

Folder
annotations/components/<view>/D<nn>/, views cmp_scan, cmp_oak1, cmp_oak2, cmp_rs
Files
images/C<shot>, labels/C<shot>.png, annotations.json (COCO), instances.json
Join
the same instance_id and key as the scanner annotations of that desktop
Labels
placement on_bench, state removed; in_sequence: false for a part only the bench shows

3D

The scanner measures depth at most of its pixels, so most of each visible mask is also a set of measured 3D points, in millimetres. Each annotated step has its reconstruction, named like its picture, and every point carries the instance and the class of the part it lies on. Nothing is filled in: a surface the scanner could not see has no points.

Scanner
reconstructions/scanner/D<NN>/S<nn>.ply: x y z in millimetres in the scanner camera frame, red green blue, instance (the value of labels/S<nn>.png at the point's pixel, 0 = none) and category (the COCO class id); format, pixel mapping and checksums in its README.md and manifest.csv. D30's reconstructions are not available yet.
Parts
select a part's points with instance, or use annotations/scanner/tools/parts3d.py, which cuts each part out of a reconstruction with the masks; steps in HOW_TO_EXTRACT_3D_PARTS.md, route and best frame per part in parts_3d_plan.csv
Cameras
Depth and point clouds of the OAK and RealSense cameras are in raw/ (.npy, .ply)

Read it right The complete extent is a silhouette on the image, not a set of points: the hidden surface of a part was never measured.

Question-answer pairs

184,263 records in 11 tasks are generated from the masks, states, relations and log. A record keeps what a model is shown (prompt) apart from the truth (label). 5,347 records form the evaluation subset; the tasks and how they are scored are under Benchmark.

Read it right Show a model the prompt only. images/ holds the frames of the evaluation subset; for any other record, the image manifest gives desktop, view and step of each frame.

Records
data/vlm_<unit>.jsonl, units scan, oak1, oak2, multi; one JSON record per line
Prompt
task, images (opaque ids), question, options, marks
Label
answer, evidence, rationale, desktop, step, split
Frames
data/vlm_<unit>.images_manifest.jsonl (id to file), images/<view>/D<nn>/s<nnn>
Subset
eval_v3/: the evaluation records per unit
Reasoning
reasoning/<unit>.jsonl: question, answer and the reasoning in words, per record, for training

  • PerceptionD19 / Step 03

    Question
    Count the cpu cooler screws that are still in place in this image.
    Answer
    {"count": 3}
    Reasoning
    The cpu cooler screws still in place are counted on the machine as it stands (a screw taken out leaves an empty hole): 3. So the count is 3.

  • ChangeD56 / Steps 12–13, before and after

    Question
    Do the pictures before and after show the same machine state, or did something change?
    Answer
    {"changed": true, "events": [{"target": "SSD storage drive", "old": "installed", "new": "removed"}]}
    Reasoning
    Comparing the two pictures, the SSD storage drive changed between the two moments. So yes, the machine changed.

  • PlanningD34 / Step 24

    Question
    Looking at the machine in these pictures, which one of the following actions is possible right now?
    • take out the RAM module
    • take out the motherboard
    • take out the CPU
    Answer
    {"verb": "remove", "target": "RAM module"}
    Reasoning
    Take out the RAM module: both its RAM latches are open, so the RAM module can be taken out. Not yet take out the CPU: the CPU socket lever still locks the CPU. Not yet take out the motherboard: the CPU and the RAM module are still mounted on the motherboard and all 6 of its motherboard screws are still in. So the one possible now is: take out the RAM module.

Questions, answers and reasoning are quoted from the records. Only the scanner image is shown here; the change and planning records also show the three cameras of the same moment.

Operator video

Two synchronised video cameras film the bench at an angle from two sides while the operator works. The recordings are cut to the moments of work and paired: 3,179 paired clips, 11.1 hours from 64 desktops, no sound, faces masked. A clip shows the action itself; the scanner frame of the same step shows its result.

Read it right These two video cameras are not the cameras of raw/, which photograph the machine after each step. When the operator looks down, a face mask can overlap the hands.

Robot demonstrations

A robot arm takes single components out in two settings: Fixtured, with parts held in slots on a base plate (1,092 episodes), and On motherboard, with parts still mounted on a board (716 episodes). A base camera and a wrist camera film each episode, recorded frame by frame with the robot's state. They are a separate recording, not the teardowns above.

Folders
raw/robot/on_fixture/raw_data/<component>/, raw/robot/on_motherboard/data/raw_data/<component>/: one episode_*.zip per episode
Frames
frame_*.pkl: timestamps, joint_positions, tcp_pose, gripper_pos, base_rgb, wrist_rgb
Episode
episode_meta.json, control_trace.jsonl
Catalog
archive_catalog.jsonl: every archive with its component, frames, bytes and SHA-256

Read it right on_motherboard/data/stage_b_pre_sft_rollouts/ holds policy rollouts, not demonstrations. Frames are Python pickles: open them only from this repository, in an isolated environment. The archives are native recordings, not a LeRobot or RLDS conversion.

See the parts together: step through one of them. To download and load the files, get started.

Benchmark: tasks and scoring

Each track fixes the input, the output, the metric and the evaluation set. Three tracks have a kit that runs now; the robot track is run on the physical system. The results of current models follow the four tracks.

  1. Kit released

    Detection and instance segmentation

    Find every part in a top-down scanner image and give its class, box and mask.

    Input
    One scanner image, 1600 × 1600 pixels, taken after a step.
    Output
    Class, score, box and mask of each part, over 24 part classes. Masks are scored either as visible masks (a part in place but fully covered is an ignore region) or as complete (amodal) masks.
    Metric
    COCO AP averaged over IoU 0.50:0.95, for masks and boxes; also AP50, AP75, AP by size, AR, per-class AP and AP by occlusion. Mean AP is taken over the 21 classes that have test instances.
    Evaluation set
    The test split: 12 desktops, 492 images, 12,930 instances. Splits are by whole desktop (split and counts).
    Kit
    benchmarks/level1/: COCO split builder, scorer with a self-check, training and prediction scripts for a YOLO segmentation model and a Mask R-CNN.

    Run it: get started, evaluate

  2. Kit released

    Visual question answering

    Answer a question about a teardown from its images, as one JSON object.

    Input
    The images of a step from one or more cameras (two moments for questions about a change), with the parts in question outlined, and the question.
    Output
    A strict JSON answer in the task's format, e.g. a list of boxes, a state, a yes or no, or a removal plan.
    Metric
    Set per task: accuracy, exact match, F1, a box hit at IoU 0.5, or a replay of a plan on the relations (task table).
    Evaluation set
    eval_v3: 5,347 questions over 11 tasks, drawn from all 66 desktops; no desktop holds more than a fifth of a task. Each record also carries its desktop's train / test split in label.split.
    Kit
    vlm/vlmpack_2026-11-05/tools/: self-check, chat converter (OpenAI, Qwen-VL and InternVL formats), scorer with reference lines (chance, most frequent answer, question without its image).

    Run it: get started, evaluate

  3. Kit released

    Depth from a single image

    Predict depth from one scanner image; the scanner's own 3D measurement is the reference.

    Input
    One scanner image, 1600 × 1600 pixels.
    Output
    A depth map of that image, in metres. A model that gives depth up to a scale is scored after alignment only.
    Metric
    As predicted: MAE, RMSE, absolute relative error, the share of pixels within a ratio of 1.25, and the median scale (predicted over measured depth). After dividing each prediction by its scale: MAE, RMSE, absolute relative error and the share within 1.05.
    Evaluation set
    The first step (S01) of D03, D04, D10, D11, D13. The reference comes from reconstructions/scanner/ and covers about half of the pixels of each picture; every desktop counts the same.
    Kit
    depth/ in the code repository: reference maps from the point clouds, and the scorer.

    Run it: get started, evaluate

  4. Data released

    Robot disassembly

    Remove the part named in an instruction and put it in the sorting zone, on the real robot.

    Input
    The instruction, and the images of the wrist and base cameras. Policies learn from 1,808 demonstrations in two settings: parts on a fixture (1,092) and parts on a motherboard (716).
    Output
    Arm and gripper actions for the whole trial.
    Metric
    Trials completed. A trial fails when it reaches 150 s or when the operator judges that the robot cannot finish.
    Evaluation
    On the system the demonstrations were recorded with (a UR5e arm with a Robotiq 2F-85 gripper), with the same instructions and home pose. Fixture: seven part categories, five fixture configurations each, ten trials per configuration (350 trials). Motherboard: 100 trials.
    Data
    The demonstrations are in raw/robot/ (layout). The track has no offline kit: it is run on the physical system.

Questions

What does "end-of-life" mean here?

Every desktop is a real, used computer that had been retired from service, from one of several brands. Each one was taken apart by hand, one step at a time.

Which views carry annotations?

The scanner view, which looks straight down on the assembly: its images carry the instance masks, the part states and the relations. The three camera views are recorded after every step as well.

Are faces visible in the operator video?

No. Faces are masked in every frame of the published clips.

Where are the scanner's 3D reconstructions?

In reconstructions/scanner/: one PLY per annotated step of 65 desktops, every point labelled with its part. The home page's explorer shows some of them in 3D. The depth and point clouds of the three cameras are in raw/, as is the robot data.

Why does the repository have a different name?

The Hugging Face repository, E3D-Desktop-Disassembly, still carries the dataset's earlier name. It holds the same data as EoL3D.
